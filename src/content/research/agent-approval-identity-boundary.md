## 执行摘要

在一次获得授权的 bug bounty 测试中，我验证了某企业 AI Agent 测试环境中的一条身份边界失效链：未登录的 Mallory 可以启动聊天任务、提交工作区文件，并对被安全护栏挂起的高风险工具操作作出“批准”。审批服务没有确认批准者是谁，也没有证明批准者拥有对应会话或操作，导致本应由可信操作者掌握的决策权落到了请求发起者手中。这不是会话窃取，也不依赖破解令牌；测试请求在无 Cookie、无有效 Authorization 的情况下即可到达这些流程。

最窄且已证实的影响是：未经认证的远程请求能够使 Agent 运行时执行命令，执行身份为 `uid=0(root)`。进一步的交互式控制也在隔离的测试实例中得到验证，但本文不会公开可复用载荷、回连方式、完整请求或审批票据。测试未接触真实用户数据，未解密或外传凭据，也未建立持久化。

我的结论来自授权环境中观察到的请求与响应、运行时配置快照、后端日志以及保留的 root 执行记录。由于无法获得后端源码、完整发布历史和确切产品版本，本文不主张源码级根因、首个受影响版本、已修复版本、厂商确认、CVE 或 CVSS 分数。

## 背景

被测系统允许模型调用文件读写、浏览器和 Shell 等工具。运行时配置显示，Shell 工具处于启用状态，工具安全护栏也处于启用状态；当命令触发敏感规则时，系统会将操作挂起，等待人工批准。这种设计的预期边界很清楚：模型可以提出操作，但只有经过认证且有权管理当前会话的人才能放行高风险动作。

本次验证涉及三类相互分离的入口：

```text
聊天流接口 ──► Agent 提议工具操作 ──► 安全护栏挂起
                                         │
上传接口 ──► 文件进入工作区              │
                                         ▼
审批接口 ──► 应由可信操作者确认 ──► 工具执行进程
```

测试拓扑只有一个授权测试实例和研究人员控制的外部验证端，不包含其他用户或生产数据。Mallory 代表一个没有登录态、Cookie 或有效令牌的网络访问者。预期行为应是在聊天、上传或审批入口处拒绝 Mallory，至少也应确保审批身份、会话所有权与待执行操作保持一致。

## 漏洞细节

我先以三种状态访问相关 API：不发送 Cookie 和 Authorization、显式省略浏览器凭据，以及发送无效的 Bearer 值。聊天流、上传和审批流程都没有因为缺少有效身份而停止。作为对照，前端虽然具备登录状态处理逻辑，但后端的这些入口并未表现出相应的强制校验。

随后，我让 Agent 请求一个会被工具安全护栏判定为高风险的操作。护栏确实工作：它没有立即执行，而是创建待审批状态并在聊天流中返回审批上下文。这证明危险命令识别并非完全失效，真正失效的是后续授权决定。

在不提供有效身份的情况下，审批接口接受了来自 Mallory 的批准。请求中携带的会话引用和审批引用均可从同一条未认证流程中获得；接口没有要求一个经过认证的审批人，也没有证明该审批人拥有对应会话。批准后，原先挂起的工具操作继续执行，结果又能通过未认证的聊天读取路径取得。

运行时配置同时解释了影响为何会继续放大：Shell 工具已启用，Agent 进程拥有 root 权限，上传文件会进入 Agent 可访问的工作区。模型本身曾多次拒绝明显带有远程控制意图的指令，这个负向控制说明模型语义防护在它能看到完整意图时有效。然而，上传与执行属于不同任务通道；当文件内容通过上传通道进入工作区，而模型只看到“运行一个工作区文件”的中性动作时，它没有获得足够上下文来判断组合后的真实效果。

因此，这条链包含两个彼此加强的设计问题：

1. 审批是一项高权限决策，却没有绑定经过认证的审批人身份与会话所有权。
2. 上传、模型判断和工具执行分别评估局部动作，没有对组合后的操作语义进行统一授权。

第二点属于典型的 confused-deputy（混淆代理）问题：每个子系统只完成自己被请求的局部工作，最终由高权限 Agent 代替未认证请求者完成了本不应允许的动作。由于缺少后端源码，我无法确认具体缺失检查位于哪个函数，也不能把运行时现象等同于源码级结论。

## 可利用性分析

证据建立的基础能力不是“绕过模型”，而是“未经认证地影响并批准高权限工具执行”。只要目标同时开放这些入口、启用 Shell 类工具，并让工具进程拥有高权限，远程访问者就可以跨越人工审批边界。保留的执行记录显示实际进程身份为 `uid=0(root)`，因此这里的 root 影响是动态验证结果，而不是从配置推测出来的结论。

验证中使用了以下正向和负向控制：

- 不发送任何凭据、显式省略浏览器凭据以及发送无效令牌时，相关流程行为一致，排除了测试依赖已有登录会话的解释。
- 高风险指令先被工具护栏挂起，证明后续执行不是简单的自动放行。
- 未认证批准后，挂起操作才继续，说明审批接口是关键边界跨越点。
- 模型对显式恶意意图进行了拒绝，但在上传内容与执行请求被拆分后未能识别组合意图，说明模型判断只能覆盖它可见的上下文。
- root 身份由实际命令执行记录确认；没有依据声称获取了其他用户身份、解密了任何密钥或建立了持久化。

完整交互式控制依赖工作区文件可被执行以及目标允许向外建立连接。在本次测试环境中，这两个条件都成立。若部署已经采用不可执行上传目录、严格出站白名单或非 root Agent 用户，影响会显著收窄；本文没有据此推断其他部署的默认状态或普遍受影响程度。

## 验证过程

出于负责任披露和降低滥用风险的考虑，本文只保留非操作化的验证顺序。完整请求、上传脚本、远程控制载荷、回连基础设施配置、真实地址、审批票据和内部标识不会公开。

```text
1. 以无登录状态请求聊天流，确认 Agent 工具入口可达。
2. 提交一个会触发安全护栏的测试操作，观察其进入待审批状态。
3. 在仍无登录状态下提交批准，确认服务端接受该决策。
4. 使用无破坏性的身份查询作为执行证明，确认工具进程权限。
5. 分别测试上传与执行通道，确认两者组合时缺少统一内容与权限判断。
```

测试过程中只使用临时、可清理的验证材料，没有访问真实用户数据，没有解密或外传秘密信息，也没有设置计划任务、系统服务、新账户或其他持久化机制。可产生直接控制能力的 PoC 仅作为私有证据保留，不应在公共环境复现。

## 修复建议

修复的核心不是增加更多提示词，而是让每一次高风险批准都成为可验证的授权决策。

审批服务至少应把以下信息绑定为一个不可替换的整体：

- 经过认证的审批人身份及其角色；
- 当前登录会话和待操作资源的所有权；
- 规范化后的完整操作摘要，例如工具名、参数、目标文件内容哈希和工作目录；
- 单次使用的随机票据、明确的短有效期以及批准后的原子失效状态。

服务端应根据这些字段生成并校验操作摘要。任何工具参数、目标文件、会话或审批人发生变化，都必须使原批准失效。审批引用不能作为权限本身，也不能仅凭“知道引用值”完成批准。对于浏览器流程，还应采用合适的 CSRF 防护，但 CSRF 不能替代身份认证和会话所有权校验。

上传与执行之间也需要建立同一条策略链：

- 上传目录与 Agent 可执行目录隔离，并使用 `noexec` 等文件系统策略阻止直接执行；
- 对可被工具消费的文件记录来源、创建者、内容哈希和审查状态；
- Shell 工具默认关闭，确有需要时只允许受控命令和参数，而不是通用解释器；
- Agent 和工具运行器使用独立的低权限账户，不以 root 身份运行；
- 使用容器、系统调用过滤、只读挂载和最小文件权限限制爆炸半径；
- 出站网络按业务所需的目的地和协议做白名单，阻断任意外连；
- 将模型安全判断保留为纵深防御，但不要把它当作身份认证、授权或沙箱边界。

回归测试应覆盖：未登录用户不能访问聊天、上传和审批入口；普通用户不能批准他人会话；过期、重复或操作摘要不匹配的批准必须失败；上传文件不可直接执行；工具进程不是 root；非白名单出站连接被拒绝。还应测试批准后再修改参数、替换文件或改变工作目录的情况，防止批准对象与实际执行对象发生漂移。

## 总结

本次授权测试确认了一条由身份缺失和任务分离共同造成的 AI Agent 边界突破：未认证访问者能够发起工具任务、取得待审批上下文并批准该任务；上传内容与后续执行又被不同组件分别判断，使高权限 Agent 成为混淆代理。最终在测试实例中观测到 root 命令执行，且进一步的交互式控制得到验证。

目前无法确认具体产品版本、首个受影响版本或修复版本，也没有厂商确认与源码级根因证据。最重要的修复方向是把审批人身份、会话、操作摘要与有效期绑定在服务端，同时让上传路径不可执行、Agent 最小权限运行并限制出站网络。模型的拒绝能力值得保留，但它只能作为纵深防御，不能承担系统安全边界。
