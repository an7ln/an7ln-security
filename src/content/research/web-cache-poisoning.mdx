缓存为了节省回源成本，会把一份响应交给多个请求复用。问题出现在一个错位上：**源站用某个输入改变了响应，缓存却没有用这个输入区分请求。** 于是，本来由一个人触发的异常内容，可能进入其他人的正常访问路径。

本文用一个浏览器内的简化实验说明这个机制。所有域名均为 `.example` 示例，实验不代表某个真实站点或 CDN 的配置，也不执行生成的资源地址。

## 01 / 先让两个人拿到同一份响应

假设我们访问 `https://blog.example/news`。站点前面有共享缓存，源站根据 `X-Forwarded-Host` 拼接页面资源来源。缺陷配置允许客户端提供的值影响源站输出，却没有把这个头部纳入缓存键。

按顺序点击“发送测试请求”和“普通读者访问”。注意两个请求携带的头部不同，但缓存键相同；第二次显示 HIT，源站没有再次参与。

然后试试反过来：清空后先让普通读者访问，再发送测试请求。已有的正常响应会让测试请求命中缓存，特殊头部根本没有机会到达源站。推进时间使条目过期，再重复实验，就能看到写入时机的作用。

## 02 / 缓存键是一次“等价性判断”

可以把缓存键理解为一个问题：哪些请求可以共享同一份响应？它不是请求报文的完整副本。方法、目标 URI 以及参与变体选择的字段共同影响缓存复用；实际产品还可能配置自定义键、查询参数处理和规范化规则。

本实验刻意只保留三个固定部分：

```text
GET | https://blog.example/news
```

现在比较这两个请求：

```http
GET /news HTTP/1.1
Host: blog.example
X-Forwarded-Host: notice.example
```

```http
GET /news HTTP/1.1
Host: blog.example
```

源站在第一次请求中生成 `https://notice.example/assets/site.js`，但缓存把响应存到普通 `/news` 的条目中。后来没有特殊头部的读者，仍然命中这个条目。**污染依赖的不是“请求头很特殊”，而是响应差异与缓存区分方式不一致。**

`X-Forwarded-Host` 只是这里选用的演示输入，不是携带它就一定存在漏洞。边缘代理可能覆盖它，源站可能忽略它，相关页面也可能根本不缓存。

## 03 / 从输入可控到跨用户影响，还差哪些条件

把验证拆成四个可以独立否定的判断，会比只寻找一次反射更清楚：

| 判断 | 需要观察到的证据 | 常见反例 |
| --- | --- | --- |
| 输入能够影响源站 | 受控标记稳定改变响应 | 代理覆盖了输入 |
| 缓存未正确区分差异 | 不同输入实际共享同一条目 | 变体已隔离 |
| 异常响应能够被存储 | 后续请求复用了异常内容 | 响应不允许存储 |
| 普通请求能够命中 | 移除特殊输入后仍收到标记 | 只有测试者的私有条目受影响 |

HIT 标记、`Age` 和重复响应可以作为线索，但不能单独证明漏洞。有些标记来自另一层缓存，有些环境不返回这些头部。关键证据是：**在受控的第二个客户端中，不再发送触发输入，仍然获得受影响的缓存响应。**

实验中的资源地址替换，只有在实际页面真的使用该地址、资源可加载并满足相应执行条件时，才可能进一步造成脚本执行。其他上下文也可能表现为错误跳转、内容篡改或可缓存错误页导致的拒绝服务；不能从一个反射点直接推导出所有这些影响。

## 04 / 三种修复，分别改变了什么

在实验里逐个切换策略，重新发送两次请求，比较缓存键和返回内容。

**把影响响应的头部加入缓存键。** 测试请求与普通请求被分到两个条目，切断本例的跨访问者复用。不过，源站仍在信任外部输入；这种方式保留了异常变体，还可能增加缓存基数。合理使用 `Vary` 或自定义缓存键，需要确认每一层缓存实际支持并采用相同语义。

**让源站使用固定、可信的资源来源。** 本例中，资源域名由部署配置决定，客户端提供的转发头不再能控制输出。如果业务确实依赖代理转发信息，应由可信代理覆盖外部同名头，并限定源站接受该信息的来源。单纯转义 HTML 并不能判断一个格式合法的资源域名是否可信。

**对相关响应使用 `no-store`。** 在遵守该指令的缓存中，新响应不会被存储，因而失去这条共享传播路径，但仍需处理源站输入问题。`no-cache` 与它不同：`no-cache` 允许存储，只是后续复用需要验证。真实部署修改规则后，也要处理已经存在的旧缓存；本实验切换策略时自动清空，不能把这种便捷行为当作生产系统的默认行为。

## 05 / TTL、清缓存与多层缓存

实验用 60 秒 TTL，点击按钮推进模拟时间后直接移除条目。真实缓存中的过期响应可能参与重验证，某些配置也允许提供陈旧内容，因此“过了 TTL”不总等同于“立刻从所有节点消失”。

边缘 CDN、反向代理和应用内部缓存还可能各自有一套键。修复最外层不保证内层也一致。分析时应分别写出每一层接收什么请求、用什么键、存储什么响应，以及由谁执行失效或清理。

清缓存能移除一次污染留下的内容；如果生成异常响应的条件还在，下一次回源仍可能重新写入。因此清理应与配置或代码修复配合。

## 06 / 在实验环境里验证，而不是只截一张 HIT

一次可审查的复现应记录：正常基线、受控输入与响应差异、缓存条目的区分方式、第二客户端的普通请求，以及修复后同一流程的结果。测试标记用无害字符串即可，先证明传播路径，再按响应上下文评估影响。

共享缓存测试会影响共享同一键的访问者。实际验证应在授权实验环境或确认隔离的缓存条目中进行；随意加一个随机查询参数不一定能隔离，因为它本身可能被缓存忽略。不要把“不确定是否入键”的参数当成隔离保证。

## 07 / 缓存投毒与缓存欺骗不是一回事

缓存投毒关注的是：**把不该共享的异常响应放进去，让后续访问者收到它。** 缓存欺骗则通常关注：诱导缓存存下原本不应公开缓存的用户敏感响应，再设法读取。两者都涉及缓存规则与应用行为的错位，但写入的内容、读取者和影响方向不同。
