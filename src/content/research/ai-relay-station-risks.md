问题不在“能不能便宜用到模型”，而在“谁能读到你的提示词、密钥和 Agent 动作建议”。第三方“AI 中转站”位于用户与模型厂商官方应用程序编程接口（API）之间。传输层安全（TLS）只保护到中转节点，请求与响应会在该节点以可处理的形式出现。结论是：把不明中转站接到带真实凭据的 Coding Agent，并把工具设为无人值守执行，会把模型链路风险放大成宿主机与云账户风险。本文只整理已公开的官方提示、研究者公开主张与测量论文，不点名未披露目标，也不提供挂马或利用步骤。

## 背景与范围

适用范围：开发者、安全研究员与团队把第三方 LLM 路由或“中转站”当作统一 API 入口，尤其是再接到可执行终端、读写文件或访问网络的 Agent。不适用于已自建、可审计且直连官方端点的企业网关。

事实依据。国家安全部微信公众号提示经广东网信网转载：部分中转站资质不清、防护薄弱，存在截留用户数据、模型名不实、后门与未评估的数据出境等风险，并建议优先官方直连、敏感数据脱敏、定期轮换凭证。[1] 中央网信办举报中心同期开设“涉 AI 应用乱象举报专区”，受理范围覆盖未履行备案、数据投毒、滥用 AI 等类别。[2]

与站内已有文章的关系：本文讨论的是模型调用链路上的不可信上游；[《自主安全智能体中的提示边界失效》](/research/autonomous-agent-boundaries/)讨论的是提示与工具边界本身。两条线可以叠在一起，但不是同一漏洞。

## 技术分析

先画信任边界，再谈危害。

```text
客户端 / Coding Agent
        │  TLS（用户 ↔ 中转站）
        ▼
第三方 AI 中转站（可读写请求与响应）
        │  TLS（中转站 ↔ 厂商）
        ▼
模型厂商官方 API
```

**事实。** TLS 在中转站处终结。用户到官方模型的加密链路被拆成两段；中转运营方可以对明文侧的提示词、系统指令、工具调用参数与模型回复做读取、截留、替换或降级。这不是“HTTPS 失效”，而是中间节点本来就被设计成必须看见业务载荷。公开技术讨论把这类中间人能力称为大模型中间人风险（LLM MITM）。[3]

**公开主张。** 2026 年 9 月，研究者 Chaofan Shou（[@shoucccc](https://x.com/shoucccc)）发帖称：从一家排名靠前的中文 LLM 路由（router）购买到一份约 6TB 的 Fable 数据集，其中可见 SSH 密钥、VPN 配置、阿里云密钥、GitLab Token 等材料，并据此主张可触及多家中国与独联体（CIS）政府实体以及小米、华为、蔚来、Minimax 等公司相关资产。[5] 这是研究者在 X 上的公开陈述，不是本文的独立复现，也不等于已完成的入侵取证。文中不转载任何密钥样本，不展开操作路径。

**测量事实（论文）。** 同作者参与的 arXiv 论文 *Your Agent Is Mine* 对 28 个付费路由与 400 个免费路由做了测量：其中 1 个付费与 8 个免费路由向返回的工具调用注入恶意代码；2 个部署自适应触发；17 个触及研究者持有的 AWS 金丝雀凭证；1 个从研究者控制的私钥钱包抽走 ETH。投毒实验还显示，泄露的上游密钥与弱配置中继会被拉进同一攻击面，诱饵侧观察到大量已处于无人值守（YOLO）执行模式的 Codex 会话。[6]

**事实。** 官方提示列出的危害类型包括：数据留存与倒卖、低配模型冒充高端模型、后门导致密钥与云凭证失窃、未合规的跨境传输。[1]

**推断（不是对某一家中转站的定责）。** 当客户端把模型返回的工具调用自动变成宿主机动作，且开启 `full access` 一类无人值守权限时，中转层对输出的任何影响都会继承本机权限。公开个案描述过：在高权限 Codex 中转链路中，出现伪装成“环境健康检查”、却尝试枚举 SSH、云配置、`.env` 与开发工具配置并向外发送的命令；该个案不足以单独证明“运营方主动植入”，但足以说明处置优先级：不可信上游不得直接驱动带真实凭据的执行环境。[4]

盘点清单（通用方法，不绑定具体产品）：

| 观察点 | 通过条件 | 失败信号 |
| --- | --- | --- |
| 上游身份 | 官方端点或自建可审计网关 | 不明域名、共享账号、无备案主体 |
| 传输边界 | 客户端密钥只打到可信网关 | API Key 直接交给第三方中转 |
| Agent 权限 | 工具调用需人工批准 | `full access` / 自动执行终端与文件读写 |
| 执行环境 | 无凭据瞬时沙盒 | 挂载 `~/.ssh`、云配置、生产 `.env` |
| 出站网络 | 官方 API 与任务白名单 | 任意域名 `POST`、任意外传 |

## 影响与限制

影响面按价值排序通常是：对话与项目资料、模型 API Key、开发机长期凭据、云与代码仓库权限。公开主张与测量论文都指向同一量级跃迁：中转层一旦留存或改写工具调用，损失从“多付一点 Token”变成“SSH、云密钥与仓库 Token 外泄”。[4][5][6]

限制：本文不把 Chaofan Shou 的帖子写成已核验的入侵报告，也不把国家安全部提示写成对全部中转站的普适定罪。arXiv 论文的数字只描述其样本与实验设置。没有 CVE，也没有厂商确认字段。

## 修复或缓解

建议与公开材料一致，按优先级排列：

1. 优先官方直连或正规授权通道；不使用无来源、无资质、无保障的入口。[1]
2. 团队需要统一入口时，自建或自管 LLM 网关，服务端长期密钥只留在网关，再直连模型提供商官方 API；网关负责鉴权、配额与审计，不替代沙盒。[4]
3. 对不明或未审查的上游，关闭无人值守执行；终端、网络与文件操作停在批准点。[4]
4. Agent 放进无凭据瞬时沙盒，不挂载 SSH、云配置、Docker Socket 与生产环境文件；出站只允许官方 API 与任务必需目标。[4]
5. 若曾在高权限模式下接入不明中转站，按“可能已暴露”处置：轮换 SSH、云密钥、GitHub Token 与发布 Token，并检查云审计与仓库访问记录。删本地配置不等于让已外传密钥失效。[1][4]
6. 使用前对个人隐私与项目资料脱敏；发现异常扣费、封号或数据异常时立即停用并留存证据。[1]
