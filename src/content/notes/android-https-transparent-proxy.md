> 整理日期：2026-10-25。案例实验发生于 2026-10-20。
>
> 本文基于一次 Android 11 真机抓包的现场记录整理。目标包名、设备序列号、业务域名和密钥均已隐去。代码中的占位符需要替换为自己的测试环境参数；展示的命令片段用于解释机制，不是一份可以直接运行的完整部署脚本。

很多 Android 抓包教程的流程很短：设置 Wi-Fi 代理，安装代理 CA，打开 Burp，然后查看请求。

但这一次，三个步骤分别撞上了三堵墙：

- 配置系统代理，会触发应用的代理环境检测。
- 保留 Root 隐藏环境后，应用又看不到注入的系统 CA。
- 为了让证书更早可见，把证书目录挂进 zygote，反而导致应用白屏、反复退出。

最后成功的关键，不是找到一个万能 Hook，而是把问题分层：**保留启动所需的隐藏环境，不经过系统代理配置，只在应用启动稳定后改变它自己的证书视图，再接通透明代理。**


![目标应用 → UID 透明转发 → 本地 9090 → adb reverse → 电脑 Burp 的抓包链路示意](/uploads/android-https-transparent-proxy/data-path.svg)

## 一、先说结论：我们到底“绕过”了什么

标题里可以统称“绕过 Root、代理和证书检测”，但技术上三件事并不相同。

| 障碍 | 最终采用的办法 | 不能据此声称什么 |
|---|---|---|
| Root / 加固环境检查 | 保持目标处于 Magisk DenyList 环境，不在启动早期增加额外 CA 挂载 | 没有证明所有 Root 检测函数都被关闭 |
| Wi-Fi / 系统代理检测 | 不设置系统代理，改在内核网络路径按应用 UID 转发 | 没有修改所有代理检测函数，也不保证其他网络检测无效 |
| TLS 证书验证失败 | 让目标进程实际看到并信任代理 CA，而不是返回“验证成功” | 没有证明所有客户端的证书绑定都被绕过 |

这次的成果是：**在指定设备、指定应用版本和已验证的网络路径上稳定抓到真实 HTTPS 请求。** 不是一套对所有 Android 应用通用的检测关闭器。

实验中没有依赖修改 APK、重签名、关闭 SELinux 或通用 Frida 信任全部证书脚本。

## 二、Root 隐藏与证书注入，为什么会互相打架

设备已经通过 Magisk 获得 Root。我们要解决的并不是“让应用获得 Root”，而是让一个对运行环境敏感的应用在这台设备上正常运行。

最终配置保留了两点：

1. 目标仍在 Magisk DenyList 中。
2. SELinux 仍为 Enforcing。

这里要避免一个常见误解：**DenyList 不是“检测函数全部返回 false”的万能开关。** 我们采用它，是因为这次设备上的稳定运行配置需要保留该环境，而不是因为已经完整反编译了应用所有 Root 检查。

问题在于，这种配置下，目标看到的文件系统挂载视图与 adb shell 不一致。我们通过模块放入系统证书目录的 Burp CA，在 shell 中存在，在目标应用中却不存在。

历史检查结果非常直观：

| 从哪里检查系统证书目录 | 证书数量 | 代理 CA |
|---|---:|---|
| init / adb shell 的视图 | 140 | 存在 |
| 目标进程的视图 | 138 | 不存在 |

于是出现了一个矛盾：

```text
保留原隐藏环境
    → 应用可以运行
    → 模块 CA 在应用视图中不可见
    → 代理的 TLS 证书无法通过验证

试图强行让 CA 提前可见
    → 改变启动环境
    → 应用又可能在早期退出
```

这时继续“多装一遍证书”没有意义。需要回答的是：**应用究竟在哪个挂载命名空间里，实际读到了什么？**

## 三、绕过 Wi-Fi 代理检测：不改系统代理，改流量路径

### 3.1 为什么不沿用普通 Wi-Fi 代理

显式代理会在系统中留下代理配置。应用如果查询这些设置，就可能发现设备处于代理环境。

我们的选择不是 Hook 这些查询接口，而是根本不写入代理配置：Wi-Fi 代理保持“无”，全局代理也不设置。

应用仍按原来的方式连接业务服务器，只有它发出的网络包，在内核 OUTPUT 路径被改送到本地代理入口。

因此，这里的“绕过 Wi-Fi 代理”准确地说是：

> **规避系统代理配置检测，使用透明转发完成抓包。**

### 3.2 按 UID 转发，而不是代理整台手机

Android 应用有对应 UID。我们只为目标 UID 处理 TCP 80/443，避免把其他应用流量也卷进来。

核心规则可概括为：

```sh
# 以下在设备 root shell 中执行；APP_UID 必须是当前目标应用的实际 UID。
# 这是 NAT 部分的机制示例，不包含完整守护、协议限制与回滚逻辑。
APP_UID='<UID>'
PORT=9090

iptables -t nat -N BURP_HZS 2>/dev/null
iptables -t nat -F BURP_HZS

iptables -t nat -A BURP_HZS -p tcp -m owner --uid-owner "$APP_UID" \
  --dport 80 -j REDIRECT --to-ports "$PORT"
iptables -t nat -A BURP_HZS -p tcp -m owner --uid-owner "$APP_UID" \
  --dport 443 -j REDIRECT --to-ports "$PORT"

# 移除旧的同名跳转后，再插入，避免重复叠加。
iptables -t nat -D OUTPUT -j BURP_HZS 2>/dev/null
iptables -t nat -I OUTPUT 1 -j BURP_HZS
```

完整方案还限制了目标 UID 的 UDP/443 和 IPv6 web 出站，减少 QUIC 或 IPv6 直连绕开这条 IPv4 TCP 代理路径的情况。

这不等于代理了任意协议、任意端口。被阻断的路径是否会回退、业务是否会重试，也需要实测，不能只看规则就下结论。

### 3.3 USB reverse 把手机本地端口接到电脑

流量先到手机本地 9090，再通过 ADB reverse 到电脑上的 Burp：

```sh
adb reverse tcp:9090 tcp:9090
adb reverse --list
```

多设备环境要显式指定正确的设备序列号。手机重启或 USB 重连后，也要重新检查 reverse，不能假定它一直有效。

最终路径是：

```text
目标应用正常连接服务器
          ↓
UID 专属 iptables REDIRECT
          ↓
手机本地 9090
          ↓ adb reverse
电脑 Burp 9090
```

Burp 的监听器需要开启 **Support invisible proxying**。因为这里不是应用主动连接一个显式代理，而是正常连接被透明转了过来。

到这一步，我们解决的是“包怎么送到 Burp”，还没有解决“应用为什么信任 Burp”。

## 四、证书验证失败：不是安装成功就算完成

### 4.1 用户 CA 与系统 CA 是两回事

该样本的网络安全配置只信任系统 CA，关键内容可归纳为：

```xml
<network-security-config>
    <base-config cleartextTrafficPermitted="false">
        <trust-anchors>
            <certificates src="system" />
        </trust-anchors>
    </base-config>
</network-security-config>
```

所以，仅在 Android 用户证书区安装 Burp CA，并不能满足这条配置的信任要求。Android 的网络安全配置允许指定应用信任的 CA 来源，系统与用户证书不是可以随意互换的同一个集合。参见 [Android 官方 Network Security Configuration 文档](https://developer.android.com/privacy-and-security/security-config)。

这份配置中没有 `pin-set`，但我们没有据此断言“应用不存在证书绑定”。代码、自定义 TrustManager、原生网络库仍可能有独立校验。

### 4.2 真正要验证的是目标进程的证书视图

只检查下面这个目录不够：

```text
/system/etc/security/cacerts/
```

因为你看到的可能是 adb shell 自己的挂载视图。

本次应检查的是：

```text
/proc/<目标当前PID>/root/system/etc/security/cacerts/
```

其中的 `/proc/<PID>/root` 提供了定位该进程根文件系统视图的入口。

检查片段如下，变量需要填成现场值：

```sh
# 在设备 root shell 中检查。
APP_PID='<PID>'
CA_FILE='<CA_HASH>.0'

ls -l "/proc/$APP_PID/root/system/etc/security/cacerts/$CA_FILE"
ls "/proc/$APP_PID/root/system/etc/security/cacerts" | wc -l
```

这里的文件存在和数量只是准备条件，最终仍要用真实 TLS 请求验证。换一个 Burp 实例后，CA 可能已经不同；旧 CA 文件还在，不代表它会信任新 Burp 签发的证书。

## 五、最重要的一次失败：把证书挂进 zygote 后白屏了

### 5.1 看起来合理的方案，实际改变了敏感的启动环境

早期思路是：既然应用看不到模块里的证书，那就把完整证书目录提前挂进 zygote，让后续进程继承。

结果不是成功抓包，而是白屏和进程反复重启。

最初很容易把它理解为网络卡住，但进一步观察发现：目标启动后很快就退出。内核信号记录中出现了目标向自身 PID 发送 `SIGKILL` 的情况，循环间隔约为 60–90 ms。

这已经不是“等 TLS 超时”的典型形态了。

### 5.2 通过对照，排除错误归因

我们没有直接写一句“检测到 Root”就结束，而是逐个改变条件：

| 对照操作 | 结果 |
|---|---|
| 关闭透明代理 | 仍发生启动退出 |
| 临时移出 DenyList | 仍不能作为稳定启动修复，随后恢复 |
| SELinux 对照 | 未解决，随后恢复 Enforcing |
| 撤掉 zygote 中旧脚本额外增加的 CA bind | 应用转为稳定，进入登录界面 |

这组结果说明：**早期手动 CA 挂载与本次启动异常有明确关联。**

但证据还不足以命名具体检测函数。更严谨的表述是：加固的早期环境检查可能对这一挂载变化敏感。这是根据对照结果作出的推断，而不是已完成的检测代码反编译结论。

同样不能把“自发 SIGKILL”写成“Magisk 杀死了应用”。信号来源与触发条件是两个不同问题。

## 六、成功方案：延迟两秒，只挂目标应用自己的 namespace

这次转折不是换了另一份证书，而是改变了**修改时机**和**修改范围**。

### 6.1 顺序比工具更重要

最后采用的顺序是：

```text
保留 DenyList、SELinux Enforcing
              ↓
应用在原始证书挂载视图中正常启动
              ↓
等待约两秒，再次确认目标 PID 未变化
              ↓
仅向目标应用的 mount namespace 绑定完整 CA 目录
              ↓
确认目标自己的视图中能读到代理 CA
              ↓
再启用目标 UID 的透明代理
```

关键挂载操作为：

```sh
# 机制片段：在设备 root shell 中执行。
# APP_PID 必须是刚确认仍属于目标且稳定存活的实时 PID。
APP_PID='<PID>'
CA_DIR='/data/local/tmp/cacerts-all'

nsenter --mount="/proc/$APP_PID/ns/mnt" -- \
  mount --bind "$CA_DIR" /system/etc/security/cacerts
```

这里的 `CA_DIR` 是保留原系统 CA、再加入代理 CA 的完整集合，不是只放一张证书的空目录。绑定完整目录时，如果漏掉原系统 CA，其他服务端的正常信任也可能被破坏。

### 6.2 为什么不先转发再挂证书

如果代理先启用，而应用此时还看不到代理 CA，新的 TLS 请求就可能立刻失败。

因此我们选择：**先稳定启动，再准备信任，最后接入代理。**

本次约两秒的等待是这个设备和版本实测可用的经验值，不是通用 Android 安全窗口。其他应用可能更早缓存信任配置，也可能持续检查环境，不能承诺照抄同一个延时就成功。

### 6.3 用 watcher 处理 PID 和 USB 变化

手工操作一次可以验证原理，但应用重开后 PID 会变，USB 拔插后 reverse 也会消失。因此我们把流程写成守护状态机：

```text
没有本地转发入口 → 撤销抓包规则，等待
应用没有运行     → 撤销抓包规则，等待
发现新的目标 PID → 暂不代理，等待约两秒
PID 发生变化     → 放弃旧 PID，重新检查
目标 CA 不可见   → 尝试应用局部 bind
目标 CA 可见     → 启用 UID 转发，记录 capture_ready
```

早期普通后台循环会随 adb/su 会话结束被收走，成功版本使用 `nohup`、`setsid` 和标准输入输出重定向，让 watcher 脱离交互会话运行。

开机入口也改成延迟启动 watcher，不再向 zygote 注入证书。开机脚本已经配置，但当时没有再次重启完成整条开机恢复流程的验收，这点需要单独保留。

## 七、为什么“抓到页面了”，验证码却可能漏掉

链路跑通后，我们又遇到一个容易误判成“另有证书检测”的问题：页面资源进入 Burp，但后续某些请求没有出现。

原因是启动阶段的直连连接池。

为了避开早期环境检查，前约两秒没有代理。应用可能已经建立直连 HTTPS 长连接，之后继续复用它。后来新增 NAT 规则，并不会追溯改写已建立连接的 conntrack 映射。

```text
启动窗口建立直连连接
          ↓
两秒后启用 NAT
          ↓
应用复用旧连接
          ↓
后续请求仍不经过 Burp
```

我们通过连接跟踪的原始/应答元组，确认了四条属于目标 UID 的残留直连。**不能只凭 `ss` 显示远端服务器地址就判断绕过了 NAT**，因为应用 socket 显示原目的地址本身并不构成充分证据。

后续处理分成两层：

1. 增加仅针对目标 UID 的残留 IPv4 web 直连防护。正常 REDIRECT 后目的端口已经变为本地代理端口，不匹配残留 80/443 直连规则。
2. 只选择经 conntrack 确认为未 NAT 的目标连接，关闭前再次核对 UID 所有权，然后按完整连接元组执行 `ss -K`。

这不是杀掉所有 443 连接，更不是重启应用。现场处理后应用 PID 没变，用户正常点击发送验证码，对应请求进入 Burp，返回 HTTP 200。

它解决的是“切换到代理后还继续复用旧直连池”的问题，不能补回启动窗口内已经完成的请求，也不能自动证明登录或会话续期成功。

## 八、我们怎样确认不是“看起来成功”

这次没有把一条 `OK` 日志当作最终结果，而是分别检查不同层面的证据。

### 第一层：应用还活着

目标 PID 稳定，能进入正常界面，不再出现早期自杀循环。

### 第二层：目标确实能看到 CA

检查的是实时目标 PID 的 `/proc/<PID>/root/...`，而不只是 adb shell 的系统目录。历史检查中，目标视图包含代理 CA，证书数量为 140。

### 第三层：网络路径确实改变

目标 UID 的转发计数随着操作增加；reverse 路径存在。对于疑似漏包连接，进一步结合 conntrack 判断。

### 第四层：Burp 收到了真实应用流量

现场历史记录里出现 H5 页面、JavaScript 和业务 POST 等真实请求，多条 HTTP 200；部分 WebView 请求头的 `X-Requested-With` 对应目标包名。后续验证码请求也完成了实际抓取。

这些是同一链路的组合证据。HTTP 200 只代表 HTTP 层响应成功，仍不能代替业务返回码、正常功能结果或真实落库验证。

### 第五层：恢复机制经过测试

应用重开后，watcher 能跟随新 PID 重新准备 CA 和转发；移除 reverse 后撤销规则，恢复 reverse 后重新抓包的路径也做过验证。

但 watcher 通过“本地端口是否监听”判断入口存在，并不等于它会完整检查电脑 Burp 的健康状态。Burp 关闭但 reverse 还在时，仍可能出现网络失败，需要及时停止抓包恢复直连。

## 九、抓到 HTTPS，不等于业务正文已经可读

成功处理系统代理和 TLS 后，我们发现部分业务 Body 仍然是 Base64 文本。这是应用层加密，与 TLS 证书信任是两层独立机制。

后续通过运行时业务代码线索、有效密钥和真实报文交叉验证，确认某个样本请求/响应采用：

```text
JSON → UTF-8 → PKCS#7 → AES-128-ECB → 标准 Base64
```

对应的只读 Burp 扩展可以在历史记录中新增“解密明文”标签，显示原始 Header 和解密正文，不修改原始报文。

本文不展开密钥恢复过程，也不公开密钥。这里只强调：**不要把业务加密的不可读 Body，再误诊为 TLS 证书检测没有绕过。**

## 十、回头看，真正有价值的是哪些经验

### 1. 不要把三种检查混成一个问题

Root 环境、系统代理设置、TLS 信任发生在不同层面。前一层通过，不代表后一层通过；后一层失败，也不一定要回头重新 Hook 前一层。

### 2. 看应用实际看到的环境

同一个路径，在不同 mount namespace 中可能对应不同内容。系统证书注入成功与否，应该以目标进程视图和真实 TLS 行为验证，而不是以 shell 中能否 `ls` 到文件验证。

### 3. 尽量缩小改动范围

这次能稳定工作的不是“全局提前挂证书”，而是“只改目标应用，并延后到稳定启动之后”。网络侧也只处理目标 UID，没有代理整台手机。

### 4. 时序问题会伪装成检测问题

白屏可能来自早期环境变化；漏包可能来自旧连接池。没有控制变量和连接级证据，就很容易把所有异常都归因于“加固太强”。

### 5. 给成功结论写上边界

这次依然存在明确限制：

- 启动前约两秒的已完成请求不会被捕获。
- 只验证了部分网络路径，没有证明所有原生 TLS 或证书绑定都已处理。
- 没有完整定位 Root/加固检测函数，也没有证明运行时持续检测不存在。
- DenyList、两秒延时、证书目录路径都具有设备和版本条件，不能直接外推。
- 验证码抓到包，不等于完整登录、自动登录或续期问题已经解决。
- 停止抓包要先停 watcher，再撤规则；不能清空系统全部 OUTPUT 规则。

## 总结

如果用一句话概括这次抓包过程：

> **保留原有 Root 隐藏环境，用 UID 透明转发规避系统代理配置检测，在目标启动稳定后，只向它自己的挂载命名空间提供可信 CA。**

我们没有让证书校验无条件通过，而是让本次验证路径上的客户端具备正确的信任条件；没有修改所有代理检测函数，而是绕开它们依赖的配置入口；没有宣称消灭所有 Root 检测，而是在特定环境中减少可见变化，并避开已经观察到的启动敏感时序。

真正让链路跑通的，是把**应用稳定性、代理路由、证书视图、连接池和业务加密**逐层拆开，再分别用证据验证。
